# 01 · 项目简报

> 本篇展开宪法 §1 到 §3 与 §7，回答"为谁做、解决什么、按什么模型做"。事实源仍是 `docs/00-DESIGN-BRIEF.md`。

---

## 1. 背景

一个人同时是学生、学生助理、竞赛组织者、算法训练者、班长与独立开发者，事务来源天然分散：课程与作业、通知与值班、例会与活动、刷题与比赛、个人项目与面试。传统做法是把这些事务塞进按身份或领域切分的目录（一个"学生组织"文件夹、一个"学生助理"文件夹），结果是：

- 同一件事在多个分区重复出现，或落在缝隙里没人管。
- 分区成为信息孤岛（silo），跨领域的相关性被结构本身切断。
- 系统只服务某一个身份，换个身份就得换一套系统。

KERNEL 的出发点是把这些事务收进**一个通用内核**，让身份与领域退化为筛选标签，而不是划分地盘的墙。

## 2. 用户画像

| 项 | 值 |
|---|---|
| 身份 | 某高校 · 工业软件专业 · 大二 |
| 工作方式 | vibecoding 重度用户，大量项目位于 `<workspace>` |
| 品味要求 | INS 黑白极简 × 瑞士国际主义 × 未来主义动效；重视体验流畅、美感、设计合理性；双主题（亮/暗） |
| 近期待办 | 准备 demo 开发实验室面试 |

### 多重身份（均为交叉筛选标签）

`role:student`（学生）· `role:assistant`（辅导员/学生助理）· `role:competition-head`（学生组织部长）· `role:acm`（算法实验室成员，Codeforces 刷题）· `role:monitor`（班长）· `role:vibecoder`（独立开发者）

这六项在系统中全部以标签（tag）形式存在，绝不作为目录分区。参见 ADR `decisions/0002-no-role-silos.md`。

## 3. 问题定义

要解决的问题不是"再做一个待办 App"，而是：

1. **捕捉要快、要低摩擦**：想到什么先扔进收件箱，不要求当场分类。
2. **组织要通用**：按可行动性组织，不按身份/学科/领域分区。
3. **分类要有界**：标签必须命名空间化并设上限，防止爆炸成不可用的标签墙。
4. **过期要重决策**：过期的条目必须"重写或丢弃"，不允许无声堆积。
5. **存量要可见**：收件箱水位、WIP 计数、逾期计数必须在总览可见，形成反馈环。
6. **回顾要短、可视**：周回顾是系统的心跳，不能变成负担。
7. **身份与领域要能交叉筛选**：同一批任务既能按上下文看，也能按身份看，且它们永远是同一批。

## 4. 设计立场：不做信息孤岛

**核心立场：身份与领域只作为视图内的交叉筛选器（tag），一级信息架构只呈现通用循环。**

含义：

- 一级导航是通用的，不出现"学生组织""学生助理"这样的分区入口。
- 身份（`role:`）、领域（`topic:`）、上下文（`context:`）都是标签命名空间。
- 任何视图都可以按这些标签交叉筛选，得到"学生身份下的高能量待办"这类查询。
- 没有任何数据被物理地锁进某个身份容器，跨界关联天然可行。

这条立场用一句话概括：**身份是滤镜，不是抽屉。**

## 5. 系统模型（研究结论）

系统模型综合六套成熟方法，各司其职，不混用。设计原则按强度排序如下。

### 5.1 设计原则

1. **单一循环**：捕捉 → 澄清 → 组织 → 执行 → 回顾（GTD 引擎）。
2. **按可行动性组织**，不按身份/学科/领域分区（PARA 精神）。
3. **一切分类有界**：标签命名空间化（`role:` `topic:` `context:`），数量设上限思路，防止标签爆炸（Johnny.Decimal 精神）。
4. **迁移即重决策**：过期项必须"重写或丢弃"，不允许无声堆积（Bullet Journal 精神）。
5. **每个存量都有排泄口**：收件箱水位、WIP 计数、逾期计数在总览可见（系统思维：存量/流量/反馈环）。
6. **周回顾是心跳**：短、可视、可自动化（平衡环）。
7. **身份与领域 = 交叉筛选标签，不是容器**（本项目"通用性"的核心）。
8. **蒸馏要懒惰**：资料只在重读时整理（progressive summarization）。

### 5.2 六套方法的分工

| 方法 | 角色 | 在 KERNEL 中承担什么 |
|---|---|---|
| GTD | 引擎 | 捕捉 → 澄清 → 组织 → 执行 → 回顾的单一循环；next / waiting / scheduled / someday 等状态 |
| PARA | 货架 | 按可行动性组织：项目 / 区域 / 资料，而非身份分区 |
| Johnny.Decimal | 有界约束 | 命名空间化标签与数量上限思路，防止分类爆炸 |
| Bullet Journal | 迁移 | 周期回顾中的"迁移或丢弃"重决策，不允许无声堆积 |
| Zettelkasten-lite | 知识子图 | 笔记的链接（links[]）与渐进蒸馏（distillLevel），只做轻量知识网络 |
| 系统思维 | 透镜 | 存量/流量/反馈环视角：水位、WIP 限额、逾期计数、趋势图（TrendBars） |

### 5.3 循环与视图的映射

| 循环阶段 | 主要落点视图 |
|---|---|
| 捕捉 | 收件箱 INBOX（快速捕捉输入框，快捷键 `c`） |
| 澄清 | 收件箱（澄清操作条：→ 任务 / → 项目 / → 笔记 / → 资源 / 丢弃） |
| 组织 | 任务 TASKS（筛选、分组）、项目 PROJECTS（看板） |
| 执行 | 总览 OVERVIEW（下一步 TOP 6）、日程 CALENDAR（日脊）、任务列表 |
| 回顾 | 回顾 REVIEW（周回顾五步流程、停滞项目清单） |
| 全周期承载 | 资料 LIBRARY、设置 SETTINGS |

## 6. 实体与轴概览

### 6.1 通用实体（v1 承载 10 类）

`inboxItem` / `task` / `project` / `area` / `goal` / `habit` / `event` / `note` / `resource` / `review`

schema 预留（不实现）：`timeLog` / `person` / `journalEntry`。

各实体的完整字段定义见 `04-DATA-MODEL.md`。

### 6.2 通用轴（6）

| # | 轴 | 说明 | 角色 |
|---|---|---|---|
| 1 | 上下文 context | 如 `@lab`、`@campus`、`@computer` | 第一筛选 |
| 2 | 时间与紧急 | `dueAt` / `deferUntil` | |
| 3 | 能量 energy | `low` / `medium` / `high` | |
| 4 | 重要性 importance | 0 到 3，决策输入而非硬排名 | |
| 5 | 状态 status | 各实体有自己的状态机 | |
| 6 | 有界标签 tags | 命名空间：`role:` / `topic:` / `context:` | |

这 6 个轴是所有视图筛选器的共同基础，也是系统"通用"的关键：不同身份的事务共享同一套轴，因此可以自由交叉。

### 6.3 信息架构

一级导航 = 通用循环（总览 / 收件箱 / 任务 / 日程 / 项目 / 资料 / 回顾 / 设置）。身份、领域、上下文、能量均为视图内**筛选器**。

视图规格、优先级与交互细节见宪法 §4；设计系统见 `03-DESIGN-SYSTEM.md`。
