# ADR-0043 · 外键引用生命周期统一（软删只隐藏 · 彻底删除才断链）

- 状态：已采纳
- 日期：2026-10-07
- 相关：ADR-0009（编辑 / 回收站）、ADR-0018（事件可写）、ADR-0019（区域 / 目标 / 习惯 + 引用护栏）、ADR-0022（界面状态保留）

---

## 1. 背景与反馈

所有者实机反馈：「我把原项目（`p-0003`）删除后，其下任务……我删除后应该把子任务归为无项目，但是这里没有，说明我的删除并没有真正删除到原数据」——任务页按 `projectId` 分组，项目已删则组头回退显示**原始 id `p-0003`**（同行「项目」列查不到又显示「—」，两处口径不一致）。

只读扫描证实这是**系统性**问题而非单点：

- `tasks t-0003.projectId → p-0003`（项目已删）
- 5 个项目的 `areaId → a-0001`（区域已删）
- `inbox.linkedIds → 已彻底删除的 t-0001 / t-0004 / e-0002`

**根因**：后端只有两处零散引用处理，且都不在删除主路径——① 区域 / 目标 409 护栏（`AREA_REF_KINDS` 还漏了 `traces`）；② AI 聚类 / 整理的 unapply 里硬编码清 `task.projectId`。项目 / 日程 / 笔记 / 资料 / 踪迹的删除走通用 `/trash` → `moveToTrash`，**完全不看引用**。

## 2. 决策

采用唯一规则：**软删只隐藏，彻底删除才断链**。

### 2.1 声明式引用表（唯一事实源）

新增 `server/refs.mjs`：`REF_EDGES = [ [target, source, field, array, mode], … ]` 描述全部实体间引用；`mode` 为 `'detach'`（彻底删除目标时清除）或 `'keep'`（历史 / 溯源，永不改写）。用一张表取代原先四处零散机制。

### 2.2 软删只隐藏（`moveToTrash` 不变）

软删除**不触碰任何引用**。所有消费方（前端渲染 + 服务端工作流判定）按「目标不在实时快照 = 未关联」解析：UI 显示 `无项目` / `—`、分组折叠到无项目、AI 整理视为无归属。因此**恢复（restore）天然无损**——引用从未被改，撤销即精确还原。代价：回收站期间原值保留（这正是无损撤销的前提）。

### 2.3 彻底删除才断链（`purgeTrash`）

`purgeTrash` 成功后执行 `detachRefsTo(kind, id)`：按表清扫全部 `detach` 入引用（标量删键 / 数组过滤），回收站与实时文件都清，单次 `serialize` + 原子写（**不调用 `commit`，避免重入 `serialize` 死锁**），追加一条审计 `ref.detach`，purge 响应回带 `detached` 计数。删除**不再被引用阻断**——区域 / 目标 409 护栏退役（引用计数保留为 UI 信息，不再阻止删除）。

### 2.4 溯源引用永不改写

`tasks.sourceInboxId`、`inbox.linkedId / linkedIds / appliedTagIds`、`reviews.staleProjectIds / staleAdvice[].projectId` 标记 `keep`，任何删除都不改写，由消费方降级呈现。

### 2.5 编辑校验统一

`updateEntity` 不再只校验任务，改为 `assertRefsExist(kind, patch)` 按表校验全部来源实体；**存在性 = 实时 ∪ 回收站**（否则编辑一条「项目已入回收站」的任务会误报 400）。保留 `parentTaskId` 的存在 + 自引用 + 成环护栏。

### 2.6 存量悬空数据修复

新增一次性维护脚本 `scripts/refs-repair.mjs`（默认预演，`--apply` 落盘；服务停用时运行），复用 `pruneDanglingRefs()`；只清 `detach` 边，`keep` 边保持字节不变。符合 AGENTS.md §4「维护脚本例外」。

### 2.7 顺带收敛

- `applyClusterCore` 去掉 `'a-0001'` 区域兜底（空区域 = 项目无区域；`createProject` / 收件箱澄清 / 一揽子应用同口径）。
- `unapplyProjectCore`（批次**新建**的项目）复用 `detachRefsTo` 断开其全部 `detach` 入引用；`organizeUnapply` 的**归入**撤销仍**按批次 `taskIds` 范围**逐条清除（不按项目整体断链——避免误伤该项目既有的其它归属）。
- 聚类 / 整理候选的「未归属」判定统一为「无实时项目」（指向已删 / 回收站项目的任务也算未归属）。
- `projectSchema.areaId` 改为可选（清除 / 无区域项目的前提）。

## 3. 边界

- 只清扫 `detach` 边；`keep` 边永不改写。
- 清扫跨文件非事务（崩溃可能半清）——本地单用户可接受；UI 解析兜底，重跑脚本或后续 purge 可收尾。
- 不做回收站期间的引用改写（不引入日志 / 不重链）。
- 不做逐类型删除特判、不做启动自动迁移、不新增端点。

## 4. 验证与证据

- `node --check server/{refs,store,index,ai,schemas}.mjs scripts/refs-repair.mjs` 0；`npx tsc --noEmit` 0；`npm run build` 退出 0。
- **存量修复实机**（安装版真实数据，服务停止后 `refs-repair --apply`）：预演列出 **6 处**悬空（5 个存活项目 + 回收站 p-0003 的 `areaId → 缺失 a-0001`）→ 应用后清除 6 条；复扫 0。
- **软删语义实机**：`tasks t-0003.projectId → p-0003`（目标在回收站）**刻意保留**——`refExistsLoose` 视为存在，保「恢复即重挂」；应用修复后仍保留（符合设计）。
- **端到端 16/16 PASS**（`.qa/probe-refs-e2e.mjs`，临时 REF-TEST 实体 + 全量清理）：建项目 → 建任务挂项目 → 软删项目（任务保留 `projectId`、项目不在实时快照）→ **彻底删除**（响应 `detached:1`，任务 `projectId` 清除）；建区域 → 建任务挂区域 → **删除区域不再 409（200）** → 彻底删除（`detached:1`，任务 `areaId` 清除）。
- 前端 `tsc` 0 / `build` 0：任务分组将缺失项目折叠为「无项目」（不再打印 `p-0003`）；详情页缺失引用降级为 `—` / `已删除项目`；区域 / 目标删除的客户端预判护栏移除（计数仅信息展示）。

（QA 期间对真实库新建 / 删除的临时实体已全部清理；审计日志留有对应条目。）

## 5. 后果

- **正面**：一张表取代四处零散机制；软删无损可撤销；彻底删除才动数据；编辑校验补全 `projects/events/notes/resources/traces` 的缺口。
- **代价**：回收站期间实时文件保留指向已删目标的引用（由消费方解析）；彻底删除有跨文件清扫。
- **约束**：不逐类型特判 / 不事务 / 不启动迁移。
