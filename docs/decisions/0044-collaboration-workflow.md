# ADR-0044 · 协作规范与质量门禁

> **文档编号**：`ADR-0044` ｜ **类别**：决策记录 ｜ **版本**：v1.0
> **创建时间**：2026-10-19 13:10:00 ｜ **最后更新**：2026-10-19 13:10:00
> **维护**：项目所有者
> **状态**：已采纳（2026-10-19）

## 背景（Context）

KERNEL 已从单人开发进入协作阶段：仓库新增两名协作者，`main` 已启用分支保护（PR + 审批 + 禁止直推）。但工程侧仍缺三样东西：

1. **可执行的协作契约**：角色、工单、分支、提交、PR、验收标准散落在对话与口头约定里。
2. **自动化门禁**：没有 CI、没有 lint、没有测试；PR 只能靠所有者手工检查。
3. **文档与代码的同步机制**：路线图、Node 版本、实体计数、ADR 索引已经出现漂移。

同时，同工作区的「揭东技术协助项目」提供了一套可直接借鉴的工程文档制度：编号目录、命名规范、文档索引、开发日志、ADR、风险清单、交接记录，以及「一次动作、三处留痕」「未记录 = 未发生」的硬规则。

## 决策（Decision）

采用**轻量版**工程协作制度，不照搬整套文档体系：

1. **单一协作入口**：新增 `CONTRIBUTING.md`，规定角色与决策权、工单九要素、通道与文件所有权（A 数据面 / B 契约 / C 视图 / D 样式 / E 文档与 QA）、分支与提交、PR 与合并、DoD 五条门禁、数据与隐私红线。
2. **工单化**：GitHub Issue 模板（任务 / 缺陷）+ PR 模板；一个工单 = 一个分支 = 一个 PR。
3. **审批与合并**：`.github/CODEOWNERS` 将每个 PR 指向所有者；`main` 保护要求 PR + 1 次审批 + 会话解决 + 禁止 force push / 删除；**只由所有者合并**。
4. **自动化门禁**：新增 `.github/workflows/ci.yml`，在 PR 上执行 `npm ci`、`npm run build`、`node --check` 全量语法检查、隐私检查、文档义务检查。
5. **三处留痕**：代码改动 → `CHANGELOG.md` + `TASK_BOOK.md`；方向性决策 → ADR；新增 / 修改文档 → `docs/README.md`；结构变化 → `docs/05-FILE-TREE.md`。
6. **风险台账**：新增 `docs/09-RISK-REGISTER.md`，编号 `R1…`，包含等级、影响、缓解、触发信号、负责人、关联与状态。
7. **文档索引纪律**：ADR 必须在 `docs/README.md` 登记；新 ADR 编号不得重复（历史重复的 `0031` 保留原名并显式登记，新编号从 `0044` 起）。

## 备选方案与取舍

| 备选 | 未采纳原因 |
|---|---|
| 照搬源项目的 `00-索引` 到 `09-风险与待决` 全套文档体系 | 对单人维护的软件仓库过重；KERNEL 已有宪法、ADR、CHANGELOG、TASK_BOOK，重复建体系会制造第二套事实源 |
| 只靠口头约定与聊天记录 | 无法审计、无法交接；协作者一换就失忆 |
| 只加分支保护，不加 CI 与文档门禁 | 分支保护只能阻止直推，挡不住「构建失败」「文档没更新」「误提交 data/」 |
| 引入完整测试框架后再开始协作 | 测试建设需要时间；先用构建 + 语法 + 隐私 + 文档门禁兜底，测试作为下一步 |

## 后果（Consequences）

正向：

- 每个 PR 的目标、范围、证据、文档义务都可检查；所有者 review 成本下降。
- 协作者可以在不碰核心面的前提下并行工作（视图 / 样式 / 文档 / QA）。
- 文档漂移、误提交、越界改动会在 PR 阶段被拦住。
- 风险从「脑子里的担心」变成可排期的台账。

代价与约束：

- 每个改动多一层工单与 PR 开销；小改动也需要走流程。
- 所有者成为合并瓶颈；需要约定响应时限（1 个工作日）。
- CI 只覆盖构建、语法、隐私、文档，**不覆盖运行时行为**；测试仍是下一步。
- `check-docs` 只做存在性与编号校验，不判断文档内容是否正确。
