# ADR-0017 · 子任务全链路 + 项目内操作

- 状态：已采纳
- 日期：2026-10-03
- 相关：ADR-0004（数据服务 · 单写者 / 校验 / 审计）、ADR-0009（详情操作 + 回收站）、ADR-0011（状态贯通 + 任务草稿确认）、ADR-0012（全站详情统一弹窗）、ADR-0015（AI 全链 · 多实体一揽子处置）、ADR-0016（聚类立项 + AI 自动化档位）

---

## 1. 背景与问题

所有者追问：

> 「项目里面的子任务又是怎么产生的？你根本没有关系」

到 Slice R2 为止，`task.parentTaskId` 已在 `server/schemas.mjs`（schema）与 `src/lib/relations.ts`（派生「父任务 / 子任务」关联）中存在，但**没有任何写入路径**：`EDITABLE_FIELDS.tasks` 不含它，`POST /api/tasks` 不接它，界面上没有输入。后果：

1. **子任务不可创建 / 不可编辑**——字段是死字段，关联区块里永远看不到「子任务」。
2. **项目详情任务行是死行**——`ProjectDetail` 里 `onOpen={() => undefined}`，点任务无反应。
3. **项目里无法新增任务**——没有「在本项目加任务」的入口。

这与所有者「项目应能自然生长出下一步 / 子任务」的期待直接冲突。本 ADR 定义 Slice R3 的两组决策：**子任务（`parentTaskId`）全链路**与**项目内操作**。

## 2. 决策

### 2.1 `parentTaskId` 是一等写入字段，服务端强制防环

**父任务关系由服务端集中校验，UI 的候选过滤只是体验优化、不作为安全边界。**

1. **可写**：`taskCreateFieldsSchema` 增可选 `parentTaskId`；`EDITABLE_FIELDS.tasks` 与 `CREATE_FIELD_KEYS` 增 `parentTaskId`。创建（`POST /api/tasks`）与编辑（`POST /api/tasks/:id/update`）均支持；编辑传 `parentTaskId: null` 即**清除**（既有 null 语义：删键）。
2. **三重护栏**（`assertValidParentTask(callerId, parentId)`）：
   - 父任务必须**真实存在**（否则 400「父任务不存在」）；
   - 不得**自引用**（`callerId === parentId` → 400「任务不能作为自己的父任务」）；
   - 不得**成环**——沿 `parentTaskId` 祖先链上溯，命中 `callerId` 即 400「父任务会形成循环引用」。守卫上限 = 任务数 + 1，防既有脏数据造成死循环。
3. **原子性**：校验在 `commit()` 之前完成，拒绝时**不写半成品**（链路中途抛错即整体不落盘）。
4. **审计**：沿用 `task.create` / `task.update`，`detail.fields` 反映本次写入字段（含 `parentTaskId`）。
5. **数据派生不入库**：「子任务列表」由运行时按 `parentTaskId` 过滤得出（`getChildTasks`），不存派生值（遵守数据纪律）。

### 2.2 子任务在任务详情内就地创建与打开

- **区块**：`TaskDetail` 增「子任务 · N」——列出直接子任务（安静整行、完成划线），点击经 `onOpenTask` 在**当前弹窗内**打开其详情。
- **就地导航**：`TaskDetailModal` 维护一个**导航栈**：打开子任务 = 入栈，底栏「← 返回」= 出栈；切换根任务时清空。避免为子任务再叠一层弹窗（ESC / 焦点争用）。
- **quick-add**：输入标题回车即建（`parentTaskId` = 当前任务），并**继承父任务的 `projectId`**（仅此一项继承，其余走服务端默认：`next` / `@computer` / `low` / `importance 2`）；toast 提供「撤销」（移入回收站）。就绪后父详情的子任务列表随数据版本刷新即时出现。
- **编辑表单「父任务」下拉**：候选 = 未完成 / 未丢弃任务，**排除自身与全部后代**（`parentTaskOptions`）防环；含「—」清除；当前父项即使已完成后也补入以正确回显。长列表用原生 `<select>` 可接受。

### 2.3 项目内操作：任务可就地打开、可按项目预填新建

- **打开任务**：`ProjectDetail` 的任务行接通 `onOpen` → 上层打开该任务详情（复用全站 `TaskDetailModal`，含完成 / 编辑 / 删除 / 子任务全动作）。
- **添加任务到本项目**：项目详情底部提供安静输入「添加任务到本项目，回车确认」——**不即时写入**，而是打开既有 `TaskDraftModal`，`projectId` **预填**为本项目（`initialProjectId`；预填项目视为「用户已定」，AI 补全不覆盖），确认后才创建（沿用 Slice O 的草稿确认纪律）。创建成功 toast 可撤销。
- **呈现方式：替换而非叠加**。`ProjectDetailModal` 用一个小型覆盖层状态机（`task` / `draft`）：覆盖层出现时项目弹窗退场，关闭后**回归项目弹窗**。这样复用两个既有弹窗组件而**不叠加** `Modal`，避免两套 ESC / 焦点陷阱 / 焦点还原互相打架。项目弹窗原有的编辑 / 删除动作不受影响。

### 2.4 边界（明确不做）

- **不自动生成子任务**：系统绝不会凭 AI / 规则自动建子任务；一律用户显式 quick-add 或编辑父任务产生（与「先确认后写入」一致）。
- **不递归搬移**：把一个任务设到某父任务下，不自动改变其子任务的父链（子任务仍指向它）。删除 / 回收一个任务也不级联处理其子任务的 `parentTaskId`（保留引用；回收站恢复即复原）。
- **不引入新依赖 / 不新增端点**：全部复用既有 `POST /api/tasks`、`POST /api/tasks/:id/update`、回收站端点。

## 3. 后果

**正面**

- `parentTaskId` 从死字段变为可用的一等关系：任务可在详情内生长出子任务，项目可自然补充任务，闭环 owner 的「关系」诉求。
- 防环 / 自引用 / 存在性校验集中在服务端一处，UI 只是过滤候选，安全边界清晰。
- 复用既有弹窗与端点，新增面小，动作矩阵保持一致。

**代价 / 已知限制**

- 任务详情「关联」区块与「子任务」区块都会出现子任务（前者是通用关系图、后者是可操作层级）——刻意保留，二者职责不同。
- 未做删除任务的级联清理：删父任务后子任务仍指向它（`getRelations` 找不到父则不渲染出链），需要时用户自行改父；这是有意的「不做隐式破坏性操作」。
- 项目详情「添加任务」只预填 `projectId`，其余字段仍由 AI 自由补全（用户可编辑）。
