# ADR-0028 · 收件箱并行解析：每条目独立 job + 有限并发调度（Slice N3）

- 状态：已采纳
- 日期：2026-10-03
- 相关：ADR-0004（数据服务 · 单写者）、ADR-0006（AI 解析升级 · SSE 过程可视）、ADR-0008（收件箱文件投递 / 生命周期）、ADR-0023（公告解析 · 通知三性）、ADR-0027（链接阅读）

---

## 1. 背景与反馈

所有者：「ai 解析改成能并行的，只要及时处理完成的 opencode 会话就行了，不然我丢快点，跑一半的 ai 解析全断了。」

旧实现的解析运行态是**全局单令牌 + 单面板**：任一新解析启动即自增全局令牌，导致此前所有在途解析的 UI 回调全部失效、流式面板被新解析接管。表现为——快速连续丢入多条内容时，先跑的解析「跑一半就断」，进度与结果面板反复被顶掉；批量解析与多文件投递则是**严格顺序**，一批跑完才轮到下一批，吞吐低。

服务端本身没有这个限制（见 §2.5 审计结论），瓶颈完全在前端的运行态模型：把「全站只有一次解析」当成了不变量。本切片把该不变量改为「**每条目各有一次解析 job**」，并用有限并发调度器统一单条、批量与多文件三条入口。

## 2. 决策

### 2.1 job 模型与令牌（前端运行态）

`src/lib/inboxAi.ts` 重构为**每条目独立 job** 的模块级调度器，对外暴露只读快照 `jobs: ReadonlyMap<itemId, InboxAiJob>`；每个 job 独立持有 `phase` / `stage` / 流式 `text` 与 `reasoning` / `result` / `error`，彼此不共享可变状态。

- **每条目令牌**：入队即登记，令牌全局单调自增。新解析只令**同一 id** 的在途结果失去回填资格（旧流回调按令牌忽略），其它条目的解析完全不受影响。
- **增量缓冲按条目分桶** + 单一共享 ~100ms 节流计时器（避免每条目各起一个 timer）。
- `lastStartedId` 供「自动展开 / 轻柔滚入」定位当前条目；`running` / `done` / `total` 驱动批量进度。
- `reconcile`（数据版本变化）时同步清理已消失条目的 job。

### 2.2 调度器与并发上限

- **FIFO 队列 + 并发上限 `AI_PARSE_CONCURRENCY = 3`**：`pump()` 在任一 job 完成后自动进位下一条，始终最多 3 条在途。
- **启动前后双重校验**：排到某条时先校验「条目仍存在且未澄清」，再校验「令牌仍当前」；不满足则以 sentinel 错误（`GONE` / `SUPERSEDED`）收尾。
- sentinel 错误**批量不计失败**（不是真实解析失败，只是被作废 / 条目已离开）。
- 并发上限固定为常量，不做设置项（见 §4）。

### 2.3 批量入口

- `startBatchAi` 走**同一调度器**并行入队，以 `done/total` 驱动进度、失败**续跑**、全部结束**一次性播报**。
- 批量期间手动触发的单条解析共享同一队列，**不影响批量计数**。
- 多文件投递的**通用**条目改用 `Promise.all` 并行；**课表类文件仍顺序**（课表草稿 store 为单例，见 ADR-0025）。

### 2.4 清理与迟到结果语义（N0.9 完整保留）

- `clearInboxAiActive()`（全局清空）拆为 `clearInboxAiJob(itemId)`（按条清理）；`src/views/Inbox.tsx` 全部调用点随改。
- **唯一作废意图 = 显式「忽略」**（`dismissedIds`）。
- 收起 / 切页 / 被接管**不丢结果**：无同 id 更新 job 时，迟到结果仍入建议缓存；job 移除后绝不复活。
- 面板按 `jobs.get(item.id)` **派生**：每条目面板独立、行尾「解析中…」按条显示、各自完成各自「AI 建议就绪」；批条文案改「已完成 done/total」。

### 2.5 服务端为何零改动（专项审计结论）

对服务端逐点审计后确认**天然并行就绪**，本切片**零服务端改动**：

| 审计点 | 结论 |
|---|---|
| opencode 会话 | 每个解析请求**新建独立 session**，不复用、无「单活动会话」约束 |
| 全局串行设施 | 无全局锁 / 单飞（single-flight）/ inflight 去重 / 信号量 |
| 唯一串行 | `server/store.mjs` 的 `writeChain`（写盘单写者，只约束解析**之后**的落盘，不挡解析本身） |
| 超时控制 | 无共享 `AbortController`；每条 prompt 独立 120s 超时，链接抓取每次独立控制器（ADR-0027） |
| SSE 断连 | 仅置标志位，不 abort 同条上游，也不影响其它条目 |

## 3. 备选与取舍

| 备选 | 取舍 | 理由 |
|---|---|---|
| 单面板串行增强（排队 + 顺序跑完再显示） | **否决** | 仍是「一条接一条」，快速投递时总时长线性增长；用户要的是并行吞吐 |
| 每条目并行（未限并发，全放） | **否决** | 快速丢十条会同时起十个 opencode 会话，本地算力被打满、单条更慢、失败面放大；故加并发上限 |
| 客户端手工 `mapLimit` 包一层 | **否决** | 与流式 token / 面板派生 / 批量进度三套状态耦合，散在多处易漏；改为**内建调度器**统一单条、批量、多文件三条入口 |
| 并发上限做成设置项 | **延后** | 常量 3 已覆盖个人使用节奏；做设置项需要额外持久化与文档，本期不引入 |

## 4. 边界

- **同 id 快速重解析**时新旧流短暂并存（无 `AbortController` 的取舍）：旧流回调全被令牌忽略，**无状态污染**。
- `withTimeout` 超时与 SSE 断连**不会 abort 底层 opencode 生成**（上游可能空转）。如需释放算力，可后续接 SDK `session.abort`，**本期不做**。
- 并发上限 3 为常量，**不做设置项**。
- 调度器只覆盖**收件箱 AI 解析**；课表草稿解析（单例 store）与其它 AI 入口不并入。

## 5. 影响面（文件）

- 前端：`src/lib/inboxAi.ts`（重构为 job 调度器）、`src/views/Inbox.tsx`（面板按 `jobs.get(item.id)` 派生、批条文案、`clearInboxAiJob` 调用点、多文件 `Promise.all`）。
- 服务端：**零改动**（见 §2.5 审计）。
- 无新增依赖；无新增端点；无数据模型变化。

## 6. 验证与证据

- `tsc --noEmit` 0；`npm run build` 0；`clearInboxAiActive` 全仓 0 引用。

QA v59（**26/26 PASS**，证据 `.qa/v59/`）：

- **三条真并行**：三行**同时**显示「解析中…」（marker=3）；完成顺序 C→B→A（延迟 1.5s / 3s / 6s），C 完成时仍有 2 条在跑（未被接管）；各卡内容逐一匹配对应 payload。
- **重解析接管**：就绪态「重新解析」→ 面板回到解析中 → 终态为新结果，无重复卡、无错误面板。

- **零残留**：9 个测试条目全清理；filesHash 与 v57 基线逐位一致；console 预期外 error 0。
